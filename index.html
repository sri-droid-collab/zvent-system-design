1Executive overview

ZVENT.AI is a speaker-program management platform for pharmaceutical companies. Think of it as a complete business application first, and an AI-powered one second.

What it does

Imagine a pharma company wants a dinner meeting where a doctor speaks to other healthcare professionals about a product. Normally, different people handle the speaker, the approvals, the invitations, the venue, attendance, expenses, compliance and payment.

ZVENT.AI brings all of that into one platform.

The problem it solves

  • Work is spread across many people and steps, so it is hard to see where a program stands.
  • Rules (who may speak, who must approve, how much may be spent) must be applied the same way every time.
  • Everything must be provable later: who did what, to which record, when and why.

The big picture in one line

Three groups of users

Internal pharma employees

Sales representatives, managers, medical affairs, compliance, event teams, finance and tenant administrators.

They create, approve, manage and reconcile speaker programs. Normal employee sessions, limited by role and data scope.

External speakers

Healthcare professionals who have been approved to take part in speaker programs.

They see only their own programs, training, calendar, materials and payment information.

HCP invitees and event devices

Invitees register for meetings. Event staff use a tablet or kiosk for check-in.

They get limited, purpose-specific access, never a full employee account.

Phase 1 and Phase 2

Phase 1: General platform Requirement

Build the business application: data model, workflows, security, integrations, reports and user interfaces. This covers 22 numbered requirements, from multi-tenancy to CRM integration.

Phase 2: AI assistant and agents Requirement

Let users ask questions and perform supported business actions in natural language, using the same permissions and business rules as the existing platform.

Design principle: Phase 2 uses the functionality built in Phase 1. The AI must never become a separate system that bypasses approvals, eligibility checks or access controls.

How to read this document

Each statement is labelled so you can tell what is decided from what is suggested:

Requirement stated in the supplied specification. Recommendation a recommended design choice (including technology examples). Needs confirmation an open policy or product decision that nobody should silently invent. Illustrative an example used only to explain an idea.

Diagram colors: blue = user-facing activity · teal = business service · purple = AI component · orange = decision or approval · gray = infrastructure · red = error or denied · green = success or outcome. Shapes also differ, so color is never the only clue.

Plain-English glossary

Tenant: one customer organization (for example Acme Pharma) and all of its data.

HCP: a healthcare professional, such as a doctor.

Role: what a user is allowed to do.

Data scope: which records a user may do it to.

SSO: signing in with the company's own identity system instead of a separate password.

State machine: a list of allowed states and the allowed moves between them.

Policy decision point: the one place that answers "may this user do this now?".

Wildcard DNS / TLS: one setting and one certificate that cover every tenant subdomain.

Outbox: a to-do list saved in the same database step as the change, so no update is lost.

Idempotent: safe to repeat; doing it twice gives the same result as once.

Dead-letter: a parking place for jobs that kept failing so a person can look at them.

Tool gateway: the checkpoint every AI action must pass through.

Prompt injection: text that tries to trick an AI into ignoring its rules.

Retrieval (RAG): finding relevant documents first, then letting the AI answer from them.

2The complete business journey

A meeting does not simply move from “created” to “completed”. It passes through controlled business steps, with a different owner and different rules at each one.

  • User action
  • Automated system check
  • Approval decision
  • Background job
  • Final outcome
  • Rejection / blocked

Five separate business states. A speaker being eligible, a meeting being approved, an event being completed, expenses being reconciled and payment being recorded are different facts. An approved meeting can later fail an eligibility recheck; a completed event can still be waiting for receipts; a reconciled event can still be waiting for payment. Never squeeze them into one status field.

Example: a dinner program in Austin Illustrative

  1. A sales representative wants Dr. Patel to speak at a dinner next month and searches the speaker directory.
  2. The backend checks whether Dr. Patel is eligible for that date, territory, brand and engagement.
  3. The representative drafts the meeting request and adds invitees.
  4. The configured approval workflow routes it to the right approvers.
  5. Once approved, the event team takes over venue, invitations and registration.
  6. Attendees check in with individual QR codes; staff capture signatures and receipts.
  7. The system creates reconciliation tasks and compares actual spend with the plan and compliance limits.
  8. Finance reviews the claims and records payment references.
  9. The meeting closes only when the required reconciliation conditions are met.

3User roles and responsibilities

The specification says roles are data, not code: an administrator can configure roles and their permissions without a developer hard-coding a new rule for each role. There are 14 named access profiles. The device profile is included alongside human roles because it also needs a defined, restricted permission set.

Four ideas that are easy to mix up

Role

What a user can do, such as approve a request.

Data scope

Which records they can do it to: their own, their team, a region, or the whole tenant.

Tenant

Which customer organization owns the data. Nothing crosses it.

Effective period

When a role assignment or territory relationship is valid (start and end dates).

Example: two users are both Reporting Managers. Their permission to approve is the same, but one supervises the Chennai team and the other the Bengaluru team, so the records they may approve differ. Illustrative

Why the backend must enforce permissions. Hiding a button in the screen is a convenience, not security. Anyone can call the API directly or change an ID in a URL. For every request the server must check: which tenant, which role is effective today, whether the record is in scope, whether the record's current state allows the action, and whether any policy requires extra approval. The database access patterns must also keep tenants apart.

SELF + territories

Initiate speaker programs and manage field-level activities.

  • Search eligible speakers and venues
  • Create, edit and submit meeting requests

Regional oversight and second-level approval.

TENANT

National or tenant-wide sales oversight.

  • Review aggregate program and budget performance
  • Perform higher-level budget approvals as configured

  • Access authorized national reports

Restriction: Cannot bypass mandatory compliance or finance controls just because their scope is tenant-wide.

TENANT

  • Coordinate speakers, venues, travel and registration

Restriction: No specific restriction listed in the source summary; normal permission and scope checks apply.

TENANT

Manage event-team capacity and exceptions.

  • Monitor operational queues and overdue work
  • Administer speaker and training operations
  • Perform authorized overrides
  • Track handovers and resolve escalated issues

Restriction: An override must be an explicit, permission-checked action with a reason and an audit record.

7.Pharma Admin

TENANT (one tenant)

Configure and administer one pharmaceutical tenant.

  • Manage users, roles, territories and organization structure
  • Configure tenant-specific workflows, settings and templates
  • Manage authorized amendments and on-behalf-of submissions
  • Configure feature flags and tenant-level policies
  • Administer the company's workspace and user lifecycle

Restriction: Limited to their own tenant. (Scope label inferred from “administer one pharmaceutical tenant”.)

8.Medical Affairs

Scope not stated

Review medical qualifications and manage training content.

  • Review speaker nomination credentials and medical suitability
  • Record review outcomes and reasons
  • Maintain onboarding and compliance-related training content as authorized
  • Support certification and training requirements

Restriction: Medical review is distinct from the final compliance decision.

9.Compliance Officer

Scope not stated

Enforce compliance review and exception handling.

  • Perform the required compliance review of nominations and programs
  • Review eligibility, applicable spending limits and exceptions
  • Handle escalated compliance issues
  • Access audit trails and compliance reports
  • Record decisions, reasons and authorized exceptions

Restriction: A user-interface override must not silently bypass a mandatory compliance rule.

10.Finance User

TENANT

Financial review and payment processing.

  • Review speaker claims and event expenses
  • Approve or reject claims within the configured policy
  • Track honoraria and reimbursements
  • Record payment references and payment status
  • Reconcile budgets, monitor ageing items, review authorized budget transfers

Restriction: Acts within the configured finance policy.

11.Speaker

SELF

Manage their own speaker-related activities.

  • View their own approved programs and calendar
  • Access authorized event materials
  • Complete assigned training
  • View reimbursement and payment status

12.Super Admin

NONE by default

Platform-level administration and support.

  • Provision and support customer tenants
  • Manage platform-level configuration and provisioning
  • Investigate operational issues through approved support procedures
  • Request temporary, audited elevation when tenant data access is genuinely necessary

Restriction: No standing access to customer business data. Provisioning access and customer-data access are separate concerns.

13.HCP Invitee

Signed link

Register for an invited program.

  • Open their personal registration link
  • Submit permitted registration information
  • Receive confirmation and calendar updates

Restriction: Access is limited to the purpose and records tied to the signed link. Survey links should be single-use and issued only to actual attendees.

14.Kiosk / Tablet Check-in Device

One meeting

Perform event-day check-in.

  • Look up attendees within the assigned meeting roster
  • Record check-in and sync the status to the platform
  • Capture authorized signatures
  • Support controlled walk-in registration, if enabled

Restriction: Device credentials are scoped to one meeting, not the whole tenant. QR codes should be time-bound and validated by the backend.

4System architecture

Think in layers, not 22 separate applications. People use the front ends, the front ends call business modules, and the modules rely on shared infrastructure.

Presentation layer

The screens and apps people use. One shared web app serves every tenant; the speaker portal, public HCP registration and tablet check-in are separate experiences with narrower access.

Application layer

The business capabilities. Each module owns its rules, data access and tests, and reuses shared authorization, tenant context and audit instead of re-implementing them.

Infrastructure layer

The shared plumbing: a tenant-aware database, file storage for bills and logos, background workers, a durable queue with transactional outbox, a secrets vault, and logging, metrics and tracing.

Start as one modular backend

The layers above are logical. For the initial build, a well-structured modular backend is a sensible starting point, with clear interfaces so that individual components can be scaled or extracted later. Not every module needs its own microservice.

4 · cont.Required behavior, suggested technology and the module map

The architecture must separate required behavior (which the specification fixes) from suggested technology (which is only an example).

Required behavior Requirement

  • One shared database with database-level tenant isolation: every tenant-owned table carries a tenant ID and every query is scoped to the tenant
  • Roles are data, not code; roles, data scope and effective dates are configurable
  • Permissions enforced by the backend for every relevant request
  • Auditable, append-only, tamper-evident record of consequential actions
  • Invitation-only users; native login plus enterprise SSO
  • A CRM adapter abstraction so another CRM can be added without rebuilding the integration
  • Phase 2 AI runs on self-hosted models and never bypasses permissions or approvals

Possible implementation Recommendation

  • Frontend: React web app with a responsive mobile UI
  • Backend: FastAPI organized into business modules
  • Database: PostgreSQL (or another relational database with transactions and strong constraints)
  • Files: S3-compatible object storage
  • Background work: a durable job queue and scheduled worker
  • Identity: OIDC / SAML with a native login
  • Reporting: indexes and reporting queries first; specialized search later if needed
  • Phase 2: self-hosted language and embedding models, a vector store and controlled tool execution

None of these technologies is mandated by the specification. The behavior, isolation, auditability and security are what matter.

5Multi-tenancy and tenant onboarding

Creating a new pharma customer should be a configuration and provisioning operation, not an infrastructure deployment. No new database, DNS record, certificate or frontend build is needed per customer.

Example: Acme Pharma joins ZVENT. They visit zvent.com, the platform suggests acmepharma.zvent.com, checks and reserves it, an administrator sets logo, colors and users, and the tenant becomes active. Employees visiting acmepharma.zvent.com then see an Acme-branded login. Illustrative

Two experiences

Central platform administration (zvent.com) creates and provisions the customer. Tenant administration manages the customer's own organization afterwards.

Persist and resume

Each step is saved. If provisioning fails while creating default roles, a retry resumes safely instead of creating a duplicate tenant.

5 · cont.Hostnames, isolation and lifecycle

One application serves every customer. The hostname tells the server which tenant is being asked for. It never proves that the user is allowed to see it.

Wildcard DNS and TLS

Set up once by infrastructure-as-code. A *.zvent.com DNS record sends every tenant hostname to the same entry point, and a wildcard certificate covers every first-level subdomain automatically.

A wildcard certificate does not cover the root zvent.com or multi-level names, so the root needs its own coverage. Because any name resolves, the app must reject unknown or inactive hostnames.

Slug uniqueness and reserved names

  • Lowercase letters, numbers and hyphens; no leading or trailing hyphen
  • Length suited to DNS labels; case-insensitive uniqueness
  • Reserved: www, admin, api, support, onboarding…
  • Reserve in a database transaction with a uniqueness constraint; two admins checking together must not both win
  • A reservation expires if onboarding is abandoned
  • No automatic reuse of a deleted tenant's slug without a policy

Recommendation conceptual schema in the source: a tenants table and a slug reservations table.

Public branding configuration

One login page fetches a small, public config for the requested hostname: tenant name, slug, logo, theme colors and login options. Nothing private: no user lists, credentials or security policy.

Validate uploads and colors, cache by tenant and config version, and never let tenant-supplied CSS or JavaScript run.

Three rules that keep tenants apart

1. Hostname alone is not authorization

Anyone can type any hostname. After login the server must derive the allowed tenant from the authenticated identity, not from the URL or from a tenant_id sent by the browser.

2. Validate tenant membership

Check that this user is an active member of the tenant the request targets, with a role that is effective today. A valid login for Northstar is not a valid login for Acme.

3. Scope every query and every job

Every tenant-owned query, background job, cache key, file path and CRM sync must carry the tenant. Row-level security in the database is a good second layer, but careful: privileged roles can bypass it.

6Authentication, roles and authorization

Who are you, are you allowed in this tenant, and may you do this to this record right now? Every request answers those questions in the same order.

The building blocks

Invitation-only native login

Users are invited, not self-registered. Native login with a password is the fallback for tenants without SSO.

SAML 2.0 and OIDC SSO

Each tenant can connect its own identity provider. SSO proves who the person is; it does not decide what they may do.

Just-in-time provisioning

A user signing in through SSO for the first time can be created automatically, subject to the tenant's rules.

Group-to-role mapping

Groups in the identity provider can map to ZVENT roles, so access follows the company's directory.

Effective-dated permissions

Role assignments and territory or manager relationships have start and end dates, and transfers can take effect on a date.

Policy decision point

One central component decides “is this permitted?”. Every protected endpoint and business operation enforces its answer.

Approval delegation

Managers can delegate approval responsibilities. A delegate acts within the delegated scope and period, and the audit shows it was on someone's behalf.

Audited support elevation

Super Admin has no standing access to customer data. Temporary elevation is requested, limited and fully audited.

Needs confirmation Role and data-scope mapping details for SSO groups, and the rules for just-in-time provisioning, depend on each tenant's identity provider and are to be confirmed with the product owner.

7Speaker eligibility and approval workflows

Speaker eligibility is not a one-time tick box. A speaker approved yesterday may be ineligible today because a contract ended or training expired. So the rules live in one central engine that is asked again at every important moment.

What the engine looks at Requirement

  • Credentials and verification status
  • Contract and brand / territory approvals
  • Rates and engagement caps
  • Training and certification, including expiry
  • Applicable policy constraints

The engine must also explain why a speaker is ineligible, and consequential changes are audited.

When it is asked Requirement

Recheck pointWhy
Speaker selectionDon't let a rep pick someone who can't be used
Meeting submissionConditions may have changed since selection
ApprovalAn approver should decide on current facts
Date changeEligibility depends on the date (expiry, caps)
Nightly recheckA background job catches changes nobody triggered

Amendments trigger revalidation

If a meeting is changed after it was submitted or approved, the system must not assume the earlier answer still holds. When relevant data changes, eligibility is rechecked and approvals re-run as configured.

Not invented here. This document does not state the exact eligibility rules, how conflicting rules are resolved, who may authorize an exception, or any numerical spending or engagement limits. Those are product-owner decisions (Section 13).

7 · cont.Why approvals are configurable state machines

Approval steps differ by tenant and change over time. So approvals should be a configurable state machine rather than a hard-coded sequence.

Definition

Describes what should happen: the steps, who can act, the conditions, the deadlines, the escalation rules and the possible outcomes. One definition per tenant and meeting type.

Instance

Tracks what is happening to one meeting: which step it is on, who decided what and when, any delegation, and the full history.

Hard-coded sequenceConfigurable state machine (recommended)
Change an approval stepDeveloper changes code and redeploysAdministrator edits the workflow definition
Different tenantsOne flow for everyone, or branching codeEach tenant has its own definition
Extra step for a large budgetNew code pathA condition in the definition (for example a configured threshold)
Explaining a decisionRead the codeRead the definition and the history of the instance
RiskPolicies drift between code and realityNeeds careful validation of definitions

Routing

Select the right workflow, route tasks to the right approvers, record decisions and rejection reasons.

Delegation and escalation

Reporting Managers can delegate. Overdue steps escalate through a service-level rule run by a background job.

Guard conditions

A transition happens only if the actor is permitted and the record's current state allows it. Concurrent approvals must not both succeed.

Needs confirmation The exact approval steps, thresholds, conditions and self-approval restrictions for each meeting type are not given. A meeting “over a configured budget threshold” may need an extra step is an example of the kind of rule the engine must support, not a stated number.

8Event operations, finance and closure

Once a program is approved it becomes an operations job. Event staff prepare, run and document the event, then the money side is checked and closed. The key idea: a program cannot close until required reconciliation is complete.

Prepare

The Event Manager receives the approved program, confirms speaker and venue, arranges travel and registration, and sends invitations. Delivery of each invitation is tracked. Scheduled sends and reminders run as background jobs, and must never fire twice.

Event day

Attendees check in with individual QR codes; staff or a kiosk capture signatures and bills. Walk-ins are allowed only if enabled. Attendance, signatures and bills become the evidence for reconciliation.

Money

Actual expenses are compared with the planned budget and per-person compliance caps. Finance reviews claims, records payment references and status, and monitors ageing items.

8 · cont.Completed, reconciled and paid are different things

Three different questions get three different answers. Mixing them up is the most common way to build a confusing finance workflow.

Event completed

The event happened and attendance was recorded. It says nothing about money.

Expenses reconciled

Required receipts are captured, actual spend matches the plan or is explained, and any per-person cap breach is resolved or formally excepted.

Payment recorded

Finance has approved claims and recorded payment references and status. Recording a payment twice is a business problem, so it must be idempotent.

The closure gate. A program closes only when the required reconciliation conditions are satisfied; otherwise the gate refuses and lists what is still open. Typical blockers are missing receipts, unresolved cap breaches and unreviewed claims.

Needs confirmation Whether an unrecorded payment must also block closure, and the exact list of blockers, are policy decisions.

Event-day and compliance controls

Check-in security Requirement

  • QR codes are time-bound and validated by the backend
  • Device credentials are scoped to one meeting, not the tenant
  • Lookups are limited to the assigned meeting roster
  • Walk-in registration only if the tenant enables it
  • Survey links are single-use and sent only to actual attendees

Per-person caps and breaches

  • The system compares actual spend with per-person compliance caps
  • A breach is flagged for the Compliance Officer
  • Exceptions need an authorized, recorded decision
  • A UI override must never silently bypass a mandatory rule

Needs confirmation Which caps apply and what counts as a breach are not defined here.

9CRM integration framework

Design the CRM integration as a pluggable integration platform, not as CRM-specific API calls scattered through the application. Connect Salesforce today, Dynamics 365 tomorrow, or another CRM later, without rewriting the Speaker or Meeting modules. Requirement for the adapter abstraction; the vendors named here are examples only.

Golden rule. Adding a CRM should mean implementing an adapter, defining its mappings and configuring its sync behavior. It should not mean changing the business logic of the Speaker or Meeting modules.

Three separate concerns

What ZVENT wants to sync

Speakers, meetings and engagements, HCP interaction history and territories. Defined once, in ZVENT's own shape.

How a CRM implements them

Its API, authentication, object and field names, and limits. Isolated inside an adapter.

How data moves reliably

Events, schedules, retries, conflict handling and monitoring. Owned by the orchestration layer.

Five ways to connect Recommendation

You do not have to pick only one. Different tenants, and even different objects, can use different approaches behind the same framework.

A. Direct CRM API adapters

Best default ZVENT talks directly to the CRM's REST, Bulk and event APIs, with OAuth2.

Best for: CRMs with accessible, well-documented APIs.

Trade-off: Needs a separate adapter per vendor, but gives full control and fewer moving parts.

B. Middleware / iPaaS

ZVENT talks to an integration platform that connects to the CRM.

Best for: Customers that mandate an integration platform or restrict direct third-party access.

Trade-off: Extra cost, another dependency and another place to fail.

C. Event-driven synchronization

CRM webhooks or change events trigger sync jobs.

Best for: Speaker, territory and engagement updates that should appear quickly.

Trade-off: Needs durable event handling, duplicate detection and recovery for missed events.

D. Scheduled batch synchronization

Workers periodically pull changes and push updates using cursors, timestamps or bulk exports.

Best for: Large HCP datasets, historical records, initial loads and APIs without events.

Trade-off: Freshness depends on the schedule and the vendor's capabilities.

E. Hybrid

Recommended, incrementally Direct adapters where supported, middleware where required, events for low latency and batches for bulk and recovery.

Best for: ZVENT's long-term platform, where customers have different CRM constraints.

Trade-off: Needs clear routing and ownership rules to avoid duplicate sync paths; more complex to operate.

Start with a direct adapter for the first CRM if its APIs allow. Keep the interface able to route through middleware, and keep event-driven and scheduled sync in the design from day one, even if you switch them on later.

9 · cont.Durable synchronization

Never make a user's meeting submission wait for several CRM calls. Separate the business transaction from the integration job, and store the to-do list in the same database transaction.

Why an outbox? Imagine the database saves the meeting, but the process crashes before publishing the CRM job. Without a recovery mechanism, ZVENT believes the meeting is saved while the CRM never hears of it. The transactional outbox saves the change and its outgoing event together; a separate publisher then sends the event to the queue.

Inbound changes

Seven ideas in simple language

Idempotency

Doing the same update twice has the same result as doing it once. A worker may update the CRM, crash before noting it, and run again; it must not create a second speaker. Use a stable external key (ZVENT's record ID stored in the CRM) and upserts.

Rate limits

CRMs only allow so many calls. Respect the Retry-After hint, throttle per connection, and give each tenant a fair share so one tenant's bulk import does not starve the others.

Checkpoints

A bookmark of how far a bulk or incremental sync has got. Move it forward only after the changes are safely stored, so a crash resumes instead of skipping or repeating work.

Duplicate events

Webhooks can arrive twice. Keep a record of processed event IDs and make processing idempotent, so a repeat changes nothing.

Partial bulk failures

In a batch of 1,000 records, 3 may fail. Store each record's outcome and retry only the ones that can succeed.

Stale updates

A retried older update must not overwrite a newer one. Carry a version number, check it before writing, and order updates per record where needed.

Periodic reconciliation

A scheduled comparison that finds missed events, deletions and drift. A webhook is a trigger, not a guarantee, so this safety net stays even when events work.

11Phase 2 agentic AI architecture

The AI assistant is a new way to use ZVENT, not a new place where business happens. It is an interaction layer on top of the trusted Phase 1 services. It does not own business rules, and it has no private door to the database.

What the agent must never bypass Requirement

Tenant isolation

Tenant comes from the signed-in session, never from the model or the prompt.

Role and data-scope checks

The same permissions as the user would have clicking through the screens, no more.

Speaker eligibility rules

The AI never decides for itself that someone is eligible. The eligibility engine does.

Approval workflows

It cannot approve its own user's request or skip a configured step.

Spending and compliance policies

A budget cap or per-person limit cannot be ignored because the user asked nicely.

Audit requirements

Every consequential action is recorded with the real user, the action and the outcome.

Trust model. The language model is useful for understanding words and writing summaries, but its output is only a proposal. Deterministic application code, the tool gateway and the existing business services decide what is allowed.

11 · cont.Read and write paths, with two worked examples

Reading and changing are different risks, so they follow different paths. Reading is checked and answered. Changing is checked, shown, confirmed, re-checked, executed and audited.

Use the right source for the right question
Kind of questionWhere the answer comes fromWhy
Current program statuses, missing receipts, payment statusAuthoritative structured data through read-only tools that call business servicesThese answers must be exactly right and current. A text search over documents could be stale or wrong.

Example 1 · A read-only question Illustrative

In-app AI assistantAcme Pharma · Sales Representative

You have 3 programs in November 2026 with no confirmed venue:

  • PRG-2041 · Cardiology dinner, Austin · 12 Nov

Each result is recorded in the audit trail.

  1. List. A read-only tool lists the pending requests in the user's approval scope.
  2. Validate. Permissions, scope, record state, eligibility and compliance are evaluated by the business services, not by the model or the user's claim.
  3. Summarize. The agent shows each proposed decision. If the user's description does not match the findings, it says so and asks.
  4. Confirm. Nothing happens without explicit confirmation of the exact list.
  5. Execute. Each approval goes through the existing approval service, which re-checks the current state. Only permitted actions run; failures are reported, not hidden.
  6. Audit. Every result is recorded individually, attributed to the real user and marked as assistant-initiated.

11 · cont.Self-hosted AI infrastructure and safety

Phase 2 specifies self-hosted models, so customer data never has to leave your infrastructure. The supporting pieces below are what make an assistant trustworthy rather than merely fluent. Requirement for self-hosting; the rest is Recommendation.

Self-hosted language model

An open-weight model run on your own infrastructure. Which model and how much capacity are not yet decided.

Self-hosted embedding model

Turns documents and questions into vectors for search, also run in-house.

Tenant-aware retrieval and vector store

Index documents with tenant and access metadata, and partition by tenant so one customer's text is never searchable by another.

Access filtering before the model

Filter by tenant and the user's access before any text reaches the model. If the model never sees it, it cannot leak it.

Prompt-injection protection

  • Treat retrieved text and record fields (notes, names, uploaded files) as data, never as instructions
  • Allow-listed, typed tools; arguments validated on the server
  • Tenant and user always come from the session, never from model output
  • Writes always need explicit confirmation and are re-validated at execution
  • Several defenses together: no single filter is trusted
  • Regularly red-team with injected documents and malicious notes

Audit logging

Record who asked, in which tenant, which tools were called with which arguments, which sources were retrieved, what the user confirmed and what happened, linked to the normal audit events.

Evaluation and monitoring

  • Golden question sets for answer correctness and source links
  • Adversarial tests: cross-tenant requests, injection, scope escalation
  • Tool-call accuracy and correct refusals
  • Regression run on every model, prompt or tool change
  • Monitor quality, latency, cost and drift in production
